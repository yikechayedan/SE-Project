PolyMetric 后端代码规范说明（Backend Coding Specification）

适用范围：

backend/PolyMetric/：Django 项目级配置与全局基础设施

backend/apps/*/：所有业务子应用（users、tasks、datasets、models、comments、system …）


0. 总原则（必须遵守）

分层清晰：配置归配置、业务归业务、视图只做编排，复杂逻辑下沉到 service。

同类文件同风格：同样功能必须写在同样的位置（例如权限永远放 permissions.py / permission class）。

不写“散装代码”：禁止把随机工具函数塞在 views.py、serializers.py、models.py 里。

不隐式、不魔法：状态码/枚举/常量集中定义；配置走 settings / env。

可测试、可维护：任何对外接口都必须能写出测试并可重复执行。

1. backend/PolyMetric/（项目级目录）规范

backend/PolyMetric/ 的职责：全局配置、路由聚合、全局中间件、Celery/任务配置、日志配置、安全配置。
禁止在此目录写具体业务逻辑（如用户注册逻辑、评测逻辑、数据集解析逻辑等）。

1.1 文件职责划分
文件	                         允许做什么	                                               禁止做什么
settings.py	                    基础配置、INSTALLED_APPS、DRF、JWT、DB、缓存、文件存储	    写业务逻辑、调用 services、读写数据库
production_settings.py	        仅覆盖生产差异项（DEBUG、ALLOWED_HOSTS、日志级别等）	    复制整份 settings、写业务代码
test_settings.py	             测试用配置覆盖（更快的密码哈希、测试 DB、禁用外部调用等）	  写业务逻辑
urls.py	全局 API                 路由聚合（include 各 apps 的 urls）	                   写具体接口实现
asgi.py / wsgi.py	             部署入口	                                               写逻辑
celery.py	                     Celery app 初始化、队列/定时任务配置	                    直接写业务函数实现
__init__.py	                      包初始化（可导出 celery_app 等）	                        乱放工具函数

1.2 配置与环境变量规范

所有敏感信息必须来自环境变量（或 .env，但不要提交到仓库）：

SECRET_KEY、数据库密码、第三方 API Key、对象存储凭证等

配置项按模块分区（推荐顺序）：

BASE/路径与安全

INSTALLED_APPS / MIDDLEWARE

数据库、缓存

DRF / JWT

CORS / CSRF

文件上传/静态媒体

Celery

Logging

示例写法（示意）：

# === Security ===
SECRET_KEY = os.getenv("DJANGO_SECRET_KEY", "dev-only")
DEBUG = os.getenv("DJANGO_DEBUG", "0") == "1"

# === DRF / JWT ===
REST_FRAMEWORK = {
    "DEFAULT_AUTHENTICATION_CLASSES": (
        "rest_framework_simplejwt.authentication.JWTAuthentication",
    ),
    "DEFAULT_PERMISSION_CLASSES": (
        "rest_framework.permissions.IsAuthenticated",
    ),
}

1.3 全局路由 urls.py 规范

只做 include，不写业务

API 前缀统一：/api/<app>/...


urlpatterns = [
    path("api/users/", include("apps.users.urls")),
    path("api/tasks/", include("apps.tasks.urls")),
    path("api/datasets/", include("apps.datasets.urls")),
]

1.4 日志 logging 规范

全局禁止 print()

每个模块用：

import logging
logger = logging.getLogger(__name__)


日志级别约束：

logger.debug：开发定位信息

logger.info：正常业务流程关键点（创建任务、开始评测、完成评测）

logger.warning：可恢复异常（第三方超时重试）

logger.error/exception：不可恢复异常（DB 写入失败、关键依赖崩溃）

2. backend/apps/（业务子应用）通用目录规范

所有 app 必须尽量统一结构：

backend/apps/<app_name>/
├── __init__.py
├── admin.py
├── apps.py
├── models.py
├── serializers.py
├── views.py
├── urls.py
├── permissions.py        # 推荐：权限集中放这里
├── services/             # 推荐：复杂业务逻辑集中放这里
│   ├── __init__.py
│   └── xxx_service.py
├── constants.py          # 推荐：枚举、状态码、固定字符串
├── tests.py
└── utils.py              # 可选：纯工具函数（无状态、无 I/O、无 DB）



3. 编码风格与基础约束（全项目统一）
3.1 命名规范

Python 文件/变量/函数：snake_case

类名：PascalCase

常量：UPPER_SNAKE_CASE

Django Model：

类名必须是实体名：EvaluationTask / Dataset / Comment

字段名语义化：created_at / updated_at / is_deleted / status

3.2 格式化与静态检查（强制建议）

格式化：black（行宽 88）或 ruff format（二选一，统一即可）

Lint：ruff（推荐）

import 排序：isort（或 ruff 内置）

3.3 import 规范

顺序必须固定：

标准库

第三方库（django、rest_framework 等）

本项目公共模块（PolyMetric.*）

apps 内部引用（apps.xxx）

禁止循环 import；跨 app 引用必须谨慎（见“跨模块协作规范”）。

4. Model（models.py）规范
4.1 只负责“数据结构”，不负责“业务流程”

可以：

字段定义、索引、约束

__str__

简单 computed property（不查 DB、不做外部请求）

禁止：

直接调用第三方 API（LLM）

在 model 方法里做复杂流程控制

把 service 逻辑塞进 save()

4.2 必备字段建议（按需要选用）

created_at = models.DateTimeField(auto_now_add=True)

updated_at = models.DateTimeField(auto_now=True)

若有软删除：is_deleted / deleted_at

4.3 约束与索引

有唯一约束就写 UniqueConstraint

高频查询字段要建索引（例如 owner、task_id、dataset_id）

5. Serializer（serializers.py）规范（DRF 核心）

Serializer 的职责：输入校验 + 输出结构定义
复杂业务逻辑必须下沉到 service。

5.1 输入 Serializer 与输出 Serializer 分离

Create/Update 用一个 serializer（严格校验）

Detail/List 用另一个 serializer（展示字段）

class TaskCreateSerializer(serializers.Serializer):
    name = serializers.CharField(max_length=128)
    dataset_id = serializers.IntegerField()

class TaskDetailSerializer(serializers.ModelSerializer):
    class Meta:
        model = EvaluationTask
        fields = ["id", "name", "status", "created_at"]

5.2 validate 规则

字段级校验：validate_<field>

跨字段校验：validate(self, attrs)

业务依赖校验（查 DB）允许存在 validate 中，但要控制复杂度：

超过 20 行的校验建议下沉到 service 或 validator 模块

5.3 禁止行为

禁止在 serializer 里：

发请求到 LLM

启 Celery task

批量写 DB（除非是 DRF 标准 create/update 但也要轻量）

6. View（views.py）规范：只做“请求编排层”
6.1 View 的标准结构

View 负责：

认证/权限（DRF 自动）

解析请求（serializer）

调用 service

返回统一 Response

禁止把核心算法写在 View。

推荐写法：

class TaskRunView(APIView):
    permission_classes = [IsAuthenticated]

    def post(self, request):
        s = TaskRunSerializer(data=request.data)
        s.is_valid(raise_exception=True)

        result = run_task_service(
            user=request.user,
            **s.validated_data
        )
        return Response(result)

6.2 View 行数限制

单个 view 类建议 ≤ 120 行

超过则说明业务逻辑放错位置（应该进 service）

6.3 查询接口规范

List API 必须支持分页（DRF pagination）

支持排序/筛选（必要时）

禁止一次性返回超大数据（评测 item 特别容易爆）

7. Service（services/）规范：业务核心必须在这里

7.1 service 命名与粒度

文件：task_run_service.py / dataset_pack_service.py

函数命名：verb_noun 风格

create_task(...)

run_task(...)

compute_metrics(...)

一个 service 函数只做一件事，避免“上帝函数”。

7.2 事务（transaction）规范

涉及多表写入必须原子化：

from django.db import transaction

@transaction.atomic
def run_task(...):
    # create task run record
    # create evaluation items
    # update status
    ...

7.3 外部依赖调用规范（LLM / 文件 / 三方）

必须封装成 client/adapter（推荐放 services/clients/ 或 app 内 utils.py）

必须有：

超时

重试

明确异常类型

日志记录（request id / task id）

8. Permission（权限）规范

权限判断必须统一，避免“有的接口能看、有的接口报 403”这种混乱。

8.1 权限放置

推荐每个 app 都有 permissions.py

对象级权限用 has_object_permission

例如“只有任务创建者或公开任务可见”：

class CanViewTask(BasePermission):
    def has_object_permission(self, request, view, obj):
        return obj.is_public or obj.owner_id == request.user.id

8.2 禁止在 View 内手写 if else 权限判断

必须抽象为 Permission class（可复用、可测试）。

9. URL（urls.py）规范

路由命名要一致：

列表：/

详情：/<id>/

动作：/<id>/run/、/<id>/publish/

示例：

urlpatterns = [
    path("", TaskListView.as_view()),
    path("<int:pk>/", TaskDetailView.as_view()),
    path("<int:pk>/run/", TaskRunView.as_view()),
]

10. 统一返回格式与错误处理规范
10.1 返回格式建议（强烈推荐统一）

推荐统一成：

{
  "code": 0,
  "message": "success",
  "data": {...}
}


或至少做到：

成功返回结构一致

失败使用 DRF 标准错误结构（但要在前端统一处理）

10.2 错误类型约束

参数错误：serializers.ValidationError

无权限：PermissionDenied

资源不存在：NotFound

外部 API 错误：自定义异常（例如 LLMRequestError）

禁止随意 raise Exception("xxx")。

11. 常量与枚举（constants.py）规范

任何以下内容必须变成常量/枚举：

task 状态：pending/running/success/failed

evaluation type：objective/subjective/adversarial

模型 provider 名称等

禁止在代码里散落 "running" 这种魔法字符串。

12. 测试（tests.py）规范（按大作业要求非常加分）

每个 app 至少覆盖：

正常流程

权限不足

参数错误

关键边界情况（空数据、超长字符串、非法文件等）

评测系统额外必须测：

同一任务重复 run 的处理

LLM 超时重试策略是否生效（可 mock）

13. 跨 app 协作规范（避免耦合爆炸）
13.1 允许的跨 app 引用

可以：

ForeignKey/ManyToMany

引用对方的公开 serializer

引用对方 constants

13.2 禁止的跨 app 引用

禁止：

A app 直接 import B app 的 service 做核心流程（会导致循环依赖与耦合）

在 A 的 views.py 直接操作 B 的模型大量逻辑

如果必须跨 app 调用逻辑：

抽象到公共 apps/system（或公共模块）提供稳定接口

或做事件/信号（signals）但要控制复杂度

14. 提交与 Git 规范（工程合作必须）

每次提交只做一类事情：feature / fix / refactor / docs / test

commit message 推荐：

feat(tasks): add run-task endpoint

fix(users): handle duplicate email registration

refactor(datasets): split packing service

禁止提交：

venv/

__pycache__/

本地数据库（如 sqlite）

大体积数据集 zip
